# 📚 Introduction

Bugs don't stop after your app is released.

Some users experience crashes that you may never see during development.

Without a crash reporting service, these issues are difficult to investigate.

Sentry automatically collects crash reports, stack traces, device information, and other useful debugging data, helping you identify and fix production issues faster.

---

# 🤔 What is Sentry?

Sentry is a real-time error monitoring and crash reporting platform.

It automatically captures:

- JavaScript errors
- Native crashes
- Promise rejections
- Unhandled exceptions
- Device information
- OS version
- App version
- Stack traces

Instead of relying on users to describe a crash, Sentry gives you detailed technical information.

---

# 🎯 Why Use Sentry?

Benefits include:

- Real-time crash reporting
- Detailed stack traces
- Device and OS information
- Release tracking
- Performance monitoring
- Error grouping
- User context

# 📦 Installing Sentry

Install the SDK:

```bash
npx expo install @sentry/react-native
```

Follow the Sentry setup guide for your project configuration.

---

# 🚀 Initializing Sentry

Initialize Sentry near the start of your application:

```javascript
import * as Sentry from "@sentry/react-native";

Sentry.init({
  dsn: "YOUR_DSN_HERE",
});
```

---

# 🐞 Capturing Errors

Capture a handled error:

```javascript
Sentry.captureMessage("Something unexpected happened.");
```

---

# 💥 Capturing Exceptions

Capture an exception:

```javascript
try {
  throw new Error("Test Crash");
} catch (error) {
  Sentry.captureException(error);
}
```

Sentry records the exception with its stack trace.

---

# 👤 User Context

Associate errors with a specific user:

```javascript
Sentry.setUser({
  id: "123",
  email: "user@example.com",
});
```

This helps identify which users are affected.

---

# 🍞 Breadcrumbs

Breadcrumbs record events leading up to a crash.

Examples:

- Screen navigation
- Button presses
- API requests
- User actions

They help reconstruct what happened before the error occurred.

---

# 🏷 Releases

Track crashes by app version.

Example:

```text
Version 1.0.0

↓

20 crashes
```

```text
Version 1.0.1

↓

0 crashes
```

Release tracking makes it easier to verify fixes.

---

# 🗺 Source Maps

Source maps translate minified production stack traces back into readable source code.

Always upload source maps for release builds.

---

# 🔍 Debugging with Sentry

When investigating an issue:

1. Open the Sentry dashboard.
2. Select the latest event.
3. Review the stack trace.
4. Check breadcrumbs.
5. Inspect device information.
6. Reproduce the issue locally.
7. Verify the fix before releasing an update.

---

# ❌ Common Mistakes

- Forgetting to initialize Sentry.
- Not uploading source maps.
- Ignoring breadcrumbs.
- Not tracking releases.
- Leaving test DSNs in production.

---

# 💡 Best Practices

- Initialize Sentry early.
- Upload source maps for every release.
- Use release tracking.
- Add meaningful user context.
- Monitor new crashes after each deployment.
